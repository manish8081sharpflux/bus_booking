# Current-State Architecture Audit

## Scope and evidence

This audit reviews the repository as of the current working tree. It includes the Ionic customer app, the React admin panel, all existing backend services, Docker Compose, the two un-applied SQL migrations, and the empty `mobile/` directory. It does not treat template UI pages as product functionality unless they call a backend API.

## Runtime inventory

| Area | Implementation | Audit finding |
| --- | --- | --- |
| Root workspace | npm project with only `concurrently`; no orchestrated build/test scripts | Not a real monorepo workspace. |
| Customer app | Ionic React 18/Vite, routes for home, placeholder bookings/offers/profile, and operator registration | Only operator onboarding calls an API; no customer booking flow. |
| Admin panel | React 19/Vite template with backend-auth adapter and operator/user API clients | Extensive template screens; operator/user management is the only connected business area. |
| Backend workspace | npm workspaces, CommonJS JavaScript services | No shared contracts, lint, test, type-check, migration runner, or CI. `inventory-service` is only an unregistered TypeScript manifest. |
| Mobile | Empty directory | Not started. |
| Delivery | One Docker Compose and shared Dockerfile | Development-only defaults, one Kafka broker, hard-coded weak secrets, no CI/CD or production manifests. |

## Existing services

| Service | Port | Current responsibility | State |
| --- | ---: | --- | --- |
| API Gateway | 4000 | CORS, request logging, `/api` reverse proxy, architecture learning endpoint | Does not authenticate, rate limit, propagate request IDs, or normalize errors. |
| Auth | 4100 | Mongo users, bcrypt password login, JWT issuance, role menu, admin user list | Roles are `ADMIN`, `OPERATOR`, `USER`; target roles are not represented. |
| Booking | 4200 | Inserts/cancels a `bookings` row and publishes `booking.events` | No authentication, validation, ownership, seat allocation, payment, idempotency, or outbox. |
| Operator | 4600 | OTP, operator registration, and CRUD | Uses legacy numeric operators table; list/read leaks all operators to any operator role. |
| Search | 4300 | Mongo `TripView` query and `booking.events` consumer | Projection has no source trip catalogue; booking events can create incomplete documents. |
| Tracking | 4400 | Redis current location plus `tracking.events` publisher | All writes and reads are public; location expires after one hour. |
| Consumers | 4500 | One Kafka consumer process | Both handlers only log events; no durable side effect or idempotency. |

## Current data and integration state

- Auth owns Mongo `users`; its JWT payload is `{ sub, mobile, role }`.
- Auth also creates PostgreSQL `menu_items` and `role_menu_items`, so it already owns data in two databases.
- Booking, Operator, and the proposed platform migration use the same PostgreSQL database. Current booking references text `user_id` and `trip_id`; it does not match the new UUID schema.
- Search owns Mongo `tripviews`, but it derives availability from booking events without a catalogue publication event.
- Tracking uses Redis only; its event is not consumed for a durable history.
- `001_platform_schema.sql` is a proposed baseline, not automatically applied. `002_inventory_ownership_and_outbox.sql` adds ownership mapping and an outbox, also un-applied.

## Critical defects before feature work

1. **Public booking and tracking mutation**: unauthenticated endpoints permit arbitrary booking creation/cancellation and trip-location writes.
2. **Broken tenant authorization**: an `OPERATOR` can read every operator; object-level membership is absent.
3. **Data-model incompatibility**: legacy numeric operator/booking tables conflict with the UUID platform schema; migrations have no executor or rollout plan.
4. **Event loss/duplication risk**: database writes and Kafka publishes are not atomic; consumers do not persist processed-event state.
5. **Secret and PII leakage**: default `JWT_SECRET=change-me`; development SMS code logs OTPs and returns OTP values; request logs are unstructured and unredacted.
6. **No input validation or consistent errors**: request bodies and query parameters reach service code directly.
7. **Direct browser-to-service calls**: frontend defaults to port 4600 and admin defaults to 4100/4600, bypassing gateway controls and yielding inconsistent origins/prefixes.
8. **No delivery assurance**: no tests, CI, health readiness, graceful shutdown, metrics, traces, backups, or deployment security.

## Kafka and ZooKeeper

Compose uses `confluentinc/cp-kafka:7.6.1` configured in ZooKeeper mode, so ZooKeeper is required **by the current Compose configuration**. It is not required by the selected Confluent Platform generation for a new deployment: Confluent Platform 7.6 supports KRaft and documents it as the default for new clusters. Replace this development topology with KRaft before production; do not remove ZooKeeper until the broker configuration is changed. See [Confluent 7.6 compatibility guidance](https://docs.confluent.io/platform/7.6/installation/versions-interoperability.html) and [Kafka basics](https://docs.confluent.io/platform/7.6/kafka/kafka-basics.html).
